# 07: 切換前已落後：待命卡片保留落後標記

**What to build:** 使用者在工具外切換帳號時，舊帳號那份已經落後的讀數成為待命帳號後，卡片仍標為「切換前已落後」，直到該帳號出現屬於它的新讀數，重新啟動後也一樣。偵測到切換的那一輪，不管距離上次掃描多久，都對舊帳號的讀數重新判斷一次落後（切換前最後一分鐘的對話也算），結果與待命讀數一起存進工具狀態。落後讀數不再只屬於使用中帳號，畫面層依卡片的角色決定文字，三種版面都有。新文案實作前先與使用者確認。

**Blocked by:** `06-query-entry-layouts-b-c.md`、`../../managed-directory/issues/04-standby-readings.md`

**Status:** resolved

- [x] 文案已與使用者確認
- [x] 縫 ① 測試：切換前落後的讀數，切換後在待命卡片上仍是落後
- [x] 切換前一分鐘內的對話也算（不因落後判定每分鐘才掃一次而漏掉）
- [x] 重新啟動後保留；該帳號的讀數換成新的（觀測時間不同）時清除
- [x] 舊格式的工具狀態檔（沒有這個欄位）讀得懂，當成沒有落後

- [x] 未落後的待命讀數的顯示不變
- [x] 既有測試全部通過

## Comments

- 依賴有兩條，理由不同：
  - `managed-directory/issues/04-standby-readings.md`（跨 feature 路徑）：待命讀數與落後旗標一起存進工具狀態，讀寫由該票集中到納管目錄 module，所以排在它之後。它又被該 feature 的 03 擋著，不必另列。帳號與綁定維護（該 feature 的 05）與本票無關，不列。
  - `06-query-entry-layouts-b-c.md`：本票要在三種版面的待命卡片加文字，排在三種版面的查詢入口都完成之後，避免同時改同一批版面檔案、並讓外框不重疊測試一次看到最終版面。
- `tracker-check` 的 S2 只認同 feature 票號，跨 feature 路徑可能誤報。
- 文案已與使用者確認：待命卡片「切換前已落後」／"Lagging before the switch"（三種版面與命令列 `list` 共用同一句）；使用中帳號仍是「有新對話，額度尚未更新」。
- 實作取捨：落後標記存在同一個讀數檔（`readings.json`）的 `_lagging` 欄位，記的是「哪個觀測時間的讀數」，讀數換了就不成立；舊檔沒有這欄位視為沒有標記。
- 命令列 `list` 的「可以執行 query」提示只在使用中（或未納管）帳號落後或待更新時出現：查詢只能查使用中帳號，待命帳號切換前已落後時提示它沒有意義。
- 既有測試 `test_standby_account_is_never_lagging` 的前提（待命帳號永不落後）被本票推翻，改為「待命帳號不理會切換之後的對話」。
- 已知限制：①切換只偵測一次，那一輪讀數檔讀不到就整輪重試（不推進上一輪的觀測），所以標記不會漏；②若標記已寫成、之後的 `append_switch` 或 `write_observed` 才失敗，下一輪重試會重新判斷，這時新帳號的對話可能已出現，原本不落後的標記可能誤翻成落後（機率極低，落後標記只會讓使用者多查一次）；③工具晚於實際切換才偵測到時，那段時間的新帳號對話也會算進去。
