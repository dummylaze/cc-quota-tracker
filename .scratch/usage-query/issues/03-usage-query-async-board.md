# 03: 非同步查詢、冷卻與看板的查詢狀態

**What to build:** 核心提供不阻塞的查詢入口，供 GUI 使用：觸發後立刻返回，poll 只檢查子行程狀態，視窗不凍結。看板新增查詢狀態：進行中、冷卻中（手動查詢完成後 30 秒）、最後一次失敗的原因。進行中與冷卻中不能再次觸發；失敗不清空原本的讀數。查詢進行中發生切換時，查回來的讀數依額度快取裡的帳號識別碼歸屬，不會算到錯的帳號。查詢狀態只存在記憶體。畫面層在本票不動。

## Comments

- 實作：`Core.start_query()`（不阻塞，進行中或冷卻中回傳 `False`）、`poll()` 開頭先檢查進行中的查詢（先於讀額度快取，剛寫回的讀數同一輪就看得到）、`Board.usage_query`（`in_progress`、`cooling_down`、`last_failure`）。沿用 01 的 `UsageQuery.start`／`check`；同步的 `query_usage()` 與非同步共用 `_open_query()`。
- 實作前與使用者確認：手動查詢**失敗也冷卻 30 秒**（spec 只寫「完成後」）；最後一次失敗原因**進行中、冷卻中仍保留，下一次查詢成功才清除**。找不到 `claude` 時 `start_query` 仍受理，立刻記失敗並開始冷卻。
- 冷卻從「子行程結束」起算，不是從「讀數寫回」：成功判定後要等 Claude Code 自己結束才回報，正常幾十毫秒，卡住時最久拖到逾時（20 秒）。這段期間看板已是新讀數、`in_progress` 仍為 True。
- 畫面層未動，GUI 尚未呼叫 `start_query`，由 04 接線；GUI 關閉時還在跑的查詢，關閉輸入後 Claude Code 會自己結束，核心沒有提供主動結束查詢的入口，04 接線時再評估要不要。
- 測試：`tests/test_usage_query_async.py`；假 `claude` 新增選填的 `gate`（檔案出現前不回應 `get_usage`），讓測試決定查詢何時完成。
- 結案後補記（2026-10-02）：上面「GUI 關閉時還在跑的查詢……04 接線時再評估要不要」在 04 結案時沒有被接住；已另開 `.scratch/usage-query/issues/09-close-with-query-in-progress.md` 評估。
