# 03: 用量帳本

**What to build:** 報表的資料來源改成用量帳本：把對話紀錄算出的 token 數依「UTC 小時 × 帳號識別碼（或未歸屬）× 模型」追加存下，Claude Code 刪掉舊的對話紀錄之後，那段用量仍然看得到。另提供一個只更新帳本、不產生 HTML 的參數，給懸浮視窗的每日更新用（09）。

**Blocked by:** 02

**Status:** resolved

## Acceptance criteria

- [x] 帳本只存 token 數（各種類），不存金額；只追加、不改寫
- [x] 只追加已經過去 24 小時以上、帳本裡還沒有的小時；最近 24 小時每次產生報表時從對話紀錄重新計算，不寫進帳本
- [x] 報表由帳本加上最近 24 小時產生；對話紀錄被刪掉後，已入帳的用量照樣出現在報表
- [x] 帳本記下最早有資料的時間與最後更新時間（失敗時含原因），報表頁首顯示兩者
- [x] 帳本放在納管目錄的工具狀態裡，收緊權限的方式比照切換紀錄
- [x] 同一時間只讓一個行程寫帳本；另一個等它寫完或跳過這次追加，報表照樣產生
- [x] 不寫進說明的參數：只更新帳本、不產生 HTML；失敗時寫進錯誤紀錄並以結束代碼表示
- [x] 測試走命令列、跑在假 home 上，涵蓋 24 小時邊界、跨 UTC 日界、刪除對話紀錄後仍保留、兩個行程同時寫入
- [x] 既有測試全部通過

## Comments

- 2026-10-21：**實作完成**。帳本是 `.state/usage-ledger.jsonl`（批次標頭宣告行數、整批全有全無），更新狀態另存 `usage-ledger-status.json`，鎖用 `usage-ledger.lock`（Windows `msvcrt`、其他 `fcntl`，行程死掉由作業系統放掉）；隱藏參數是 `report --update-ledger`。
- 票面外、實作時自補的決定（審查者逐條判斷過，皆認為合理）：
  - 沒有用量可入帳時不前進「已入帳到哪個小時之前」。
  - 對話紀錄有檔案讀不到時：原本是整次不入帳，**使用者定案改成略過讀不到的檔、其餘照常入帳**（讀不到的檔可能永遠讀不到，擋住帳本會讓之後所有用量在 Claude Code 刪紀錄後漏掉）。報表頂端照舊示警；代價是暫時鎖住的檔那次的用量補不回來，已接受。
  - 等不到鎖（上限 10 秒）是跳過，不算失敗，狀態不動。
  - 失敗原因存進狀態檔，之後成功才清掉，所以每日更新的失敗在之後的報表仍看得到；原因只用系統回報的說明，不用帶路徑的例外字串。
  - 帳本讀不懂的批次計數並以橫幅示警。
  - 帳本的帳號識別碼接在切換紀錄之後取報表鍵（切換紀錄讀不到時，帳本裡的帳號仍有鍵）。
  - 「最早有資料的時間」不另外存，每次由帳本格子加對話紀錄現算（帳本只增不減，結果等價）。
- 審查（兩軸＋變異）：Standards 無硬違規，位置錯的註解已修；判斷題未採納（`update_ledger` 放在 `token_report`、失敗種類用字串、`(cells, through)` 用裸 tuple），不影響行為。Spec 九條驗收逐條屬實。變異檢查 9 個，7 個轉紅、1 個等價（`through <= read.through` 改 `<`）、1 個全綠：對話紀錄過濾的 `>=` 改 `>`（帳本停下來的那個整點小時會整小時漏掉）——已補測試，我重跑該變異確認轉紅。
