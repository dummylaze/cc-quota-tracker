# 01: 設定置頂，視窗卻被其他視窗蓋住

> *This was generated by AI during triage.*

**What to build:** 設定是置頂時，widget 要持續維持在 Windows 的置頂層，不能只在啟動和切換偏好時設一次。已知 Windows 會讓視窗掉出置頂層、但 `WS_EX_TOPMOST` 旗標還留著（見下方 2026-10-15 兩則），而程式重新設一次置頂就能救回來。修法方向：在定期執行的時機重新宣告置頂（例如每輪 poll），而且要確認那個呼叫真的會送出 `SetWindowPos(HWND_TOPMOST)`——旗標本來就是真的，若 Tk 遇到「值沒變」就略過，重設等於沒做（手動測試是先取消再勾才救回來的）。驗收要用 Win32 的 z-order 驗，不能只驗 Tk 屬性。

- 發生當時設定檔確實是 `"alwaysOnTop": true`；視窗由開機自動啟動（登錄 `Run` 機碼）開出，執行了一段時間後被發現藏在其他視窗後面。只發生過一次，之前做過什麼操作不記得。

- 用一支照 widget 視窗設定（無邊框、透明色鍵、置頂）建的模擬視窗實測兩次（90 秒、120 秒），逐 0.5 秒讀 Win32 的 `WS_EX_TOPMOST` 與「上方是否有非置頂視窗」：

- 但它在 z-order 裡排在第 73 層，**上方壓著好幾個非置頂的一般視窗**（編輯器、通訊軟體、檔案總管、一個全螢幕以外的遊戲視窗）。上方唯一的置頂視窗是工作列。
- 也就是說：**置頂旗標還在，但視窗已經掉出 Windows 的置頂層**。程式的狀態（Tk 屬性、選單打勾）會顯示「置頂中」，實際上不是。這跟第一次的推測「程式自己關掉了 `-topmost`」不同——程式沒有關，是 Windows 那邊的層級跑掉了。
- 發生前做過什麼仍不清楚；這段期間有開過一個 Unity 遊戲。

### 更正與手動測試結果（2026-10-15）

- 回報者確認：發生當下右鍵選單的「置頂」**是打勾的**；取消後再勾回去，視窗**恢復置頂**。

### 實作（2026-10-15）

> *This was generated by AI during implementation.*

- 每次套用偏好（每輪 poll，以及從選單改偏好時）都用 Win32 檢查視窗還在不在置頂層：自己的 `WS_EX_TOPMOST` 掉了，或 z-order 上方出現任何非置頂視窗，就重新設一次 `-topmost`。判斷在 `cc_quota_tracker/zorder.py`。
- **只在掉層時才重設，不是每輪無條件重設**（實作前與回報者確認）。實測無條件重設會蓋住開著的右鍵選單（選單開著時 Tk 的計時器照跑），也會每 5 秒跟其他置頂程式搶最上層。
- 票面擔心「值沒變時 Tk 會略過」：實測不會。對已是真的 `-topmost` 再設一次真，Tk 照樣送出 `SetWindowPos`，視窗會回到置頂層最上面。另外在 Windows 上，連**讀取** `-topmost` 都會重新套用置頂，所以測試不能用它當觀察點。
- 驗收：`tests/test_topmost.py` 用 Win32 的 z-order 驗三件事：掉到一般視窗下面後，下一輪會回來；還在置頂層時不會跳到其他置頂視窗上面；設定成不置頂時不會被拉回來。真實桌面重現不了票上的確切狀態（「旗標還在、上方卻有一般視窗」——Windows 把置頂視窗排到一般視窗後面時會一併清掉旗標），所以那條判斷改用替身驗。
- 觸發原因仍不明。修好的是使用者看得到的症狀：掉層後最多一輪 poll（約 5 秒）就會回來。
