# 01: 以 statusLine 的 rate_limits 作為第二個額度資料源（重新評估 ADR-0001、ADR-0006）

**What to build:** 額度快取只在 Claude Code 執行 `/usage`、登入、面板刷新時才更新，持續對話時工具系統性落後，使用者每次都要手動執行 `/usage`。Claude Code 交給 statusLine 的資料每次回應後都帶有最新的工作階段窗口與週窗口用量。評估是否、以及如何讓工具也取得這份資料，並決定 ADR-0001、ADR-0006 要不要修訂。

**已確認（文件或實測）：**

- Claude Code 官方 statusline 文件：statusLine 指令從 stdin 收到的 JSON 有 `rate_limits.five_hour` 與 `rate_limits.seven_day`，各帶 `used_percentage`（0～100）與 `resets_at`（Unix 秒）。只對 Pro／Max 訂閱者出現，而且要等 session 的第一個 API 回應之後才出現；每個窗口可能各自缺席，過了 `resets_at` 就不再帶。
- 同一份文件的更新時機：session 開始、每則新的助理訊息、`/compact` 結束、權限模式改變等事件，以及窗口到達 `resets_at` 時；可另設 `refreshInterval` 定時重跑。
- 這份 JSON 不帶帳號識別碼，也沒有範圍週限額、額外用量、花費、用量去向等欄位。
- 使用者既有的 statusLine 腳本已經在讀這兩個值，實際使用時每輪都會更新（實測）。
- 額度快取在持續對話時可停在一小時前（實測，見 `.scratch/usage-refresh-hint/issues/01-usage-refresh-hint.md` 的 Comments）。
- 程式碼、README、spec 都沒有 statusLine 資料源的實作；`.out-of-scope/` 不存在。

**會碰到的既有決定：**

- ADR-0001〈Considered Options〉：「自備 statusLine 腳本當第二資料源：暫不做」，理由是佔用使用者唯一的 `statusLine` 設定；當時沒有記下「只讀額度快取會系統性落後」這個代價。
- ADR-0006：不註冊 statusLine、部署說明不附 `settings.json` 範例（避免照抄的人蓋掉原本的 statusLine）。
- README 兩個語言版本的開頭承諾「不掛 statusLine」；M1 spec 使用者故事 60 同義。M1 spec 已 resolved，任何修訂都放在這個新 feature。
- ADR-0001 的「不發任何網路請求」不受影響：statusLine 的資料是 Claude Code 自己的回應附帶的。

### Grill 結論（2026-10-02）：wontfix

- VS Code 面板模式不會執行 `statusLine`（實測，面板對話期間 statusLine 寫出的檔案近 50 小時沒有更新），而面板是主要使用情境；hook 事件也不帶額度資料。statusLine 資料源只對終端機使用有效，划不來。
- 改走「查詢額度」：工具請 Claude Code 送 `get_usage`，由 Claude Code 寫回額度快取。見 `docs/adr/0010-usage-query-via-claude-code.md`；規格與票開在新 feature `.scratch/usage-query/`。
- 票面題 3～7（檔案格式、歸屬、合併、多 session、落後讀數定義）隨本票一起不做；題 8 見 `.scratch/usage-refresh-hint/issues/01-usage-refresh-hint.md` 的 Comments。
