# M1 唯讀監控

Status: ready-for-agent

## 問題陳述（Problem Statement）

同時持有好幾個 Claude 帳號的人，沒辦法一眼看到每個帳號各自還剩多少額度、什麼時候重置。Claude Code 只顯示使用中帳號的數字，一旦切換帳號，前一個帳號的用量就從視線裡消失了；想知道就只能切回去，或是在該帳號下打開 `/usage`。帳號越多，越難判斷「這週哪個帳號還有餘裕」。

另外，登入憑證會悄悄過期。等到要切回某個帳號時才發現憑證已失效，使用者通常搞不清楚發生了什麼事。

## 解決方案（Solution）

一個 Windows 桌面懸浮小視窗，常駐並可設為置頂：

- **精簡模式**只顯示使用中帳號的工作階段窗口與週窗口：進度條、重置倒數、讀數年齡、憑證到期倒數。
- **展開模式**顯示每個納管帳號的卡片，使用中帳號會高亮；待命帳號顯示最後一次觀測到的用量讀數和它的相對年齡。

所有數字都來自 Claude Code 自己維護的本機檔案，工具不發任何網路請求（ADR-0001）。帳號可以從命令列或視窗的右鍵選單納管：在 Claude Code 登入某個帳號後執行 `add <標籤>`（或選「納管目前登入的帳號…」），就把該帳號的憑證快照交給本工具保管。M1 以原始碼方式部署（需要本機有 Python），不打包成 exe。

工具會分辨「讀數舊」和「讀數落後」：帳號沒在用時，舊讀數依然準確，不會發出警示；只有讀數之後本機又有新的對話活動時，才會提醒使用者這個數字已經落後。

## 實作決策（Implementation Decisions）

### 資料來源與解析

- 用量讀數只來自 `~/.claude.json` 的 `cachedUsageUtilization`。它的頂層只有三個鍵：觀測時間 `fetchedAtMs`、帳號識別碼 `accountUuid`，以及 `utilization`，其餘所有內容都在 `utilization` 之下。
- **單一解析層**：Claude 供應商模組只對外提供一個解析入口，把原始 dict 轉成用量讀數，或轉成下列三類解析結果之一。解析層以外的程式永遠不碰原始 dict。
  - **暫時不可讀**（JSON 解析失敗，通常是讀到寫入中的檔案）→ 保留上一次的值，靜默重試，不告警。
  - **尚無讀數**（`cachedUsageUtilization` 不存在）→ 屬於正常狀態，不告警。
  - **結構不符**（有 `utilization`，但 `limits` 不是 list、元素缺 `kind` 之類）→ 連續 3 輪才亮結構變更橫幅。區分三類靠症狀；「連續 3 輪」只是保險，不是區分手段。
- 限額以 `utilization.limits[]` 為主，用 `kind` 判讀種類；`five_hour`／`seven_day` 的百分比只作交叉校驗，金額欄位與鎖定原因從它們取。
- `is_active` 只存在於 `limits[]` 的元素裡，意思是**供應商挑的頭條列**（只能顯示一個數字時該顯示哪一列），**不代表窗口是否在計時**：實測計時中、63% 的工作階段限額也會是 `false`。看板把它當頭條旗標帶出，不拿來判定計時中窗口。
- 不寫死限額種類：不認得的 `kind`，加上 `utilization` 底下「形狀含 `utilization` 鍵、非 null、不在已知清單內」的欄位，一律歸入其他限額，以原始名稱呈現。
- 範圍週限額：`limits[]` 中 `kind` 為 `weekly_scoped` 的列，範圍名稱取 `scope.model` 或 `scope.surface` 的 `display_name`；沒有這種列時，才採用非 null 的 `seven_day_opus`／`seven_day_sonnet`，避免重複。
- `resets_at` 是 ISO 8601 字串。`resets_at` 為 null，或現在時間已到某限額自己的 `resets_at` 時，該限額判定為沒有計時中窗口，下次重置時間標為未知；不推算下一個重置時間。這個判定每輪 poll 以當下時間重做，來源檔案沒變也會生效。週窗口例外：它固定 7 天、與閒置無關，過了 `resets_at` 代表新的一週已經開始，所以標為已重置（用量與下次重置時間要等新讀數），不顯示成無計時中窗口。
- 嚴重度以 `limits[].severity` 為主（供應商的值域是 `normal`／`warning`／`critical`），不認得的值一律當 `normal`；欄位缺失或為 null 時才退回百分比門檻（設定檔 `providers.claude` 的 `warningPercent`／`criticalPercent`，預設 60／85%）。這個推定在核心每輪建卡片時做，不在解析時做：改了門檻，下一輪就生效，不必等額度快取更新。
- schema 判定在每一輪都做，不只在啟動時做一次。解析耗時約 1 ms。**一輪＝一次 poll**：來源檔案沒變、不重新解析的輪次，沿用上一次的解析結果，照樣計入「連續 3 輪」；否則結構改版後檔案不再變動，橫幅就永遠不會亮。暫時不可讀與偶發讀取失敗的輪次不計入，也不歸零。

### 帳號身分與切換（ADR-0002）

- **憑證儲存介面**（CredentialStore）：提供讀取、憑證指紋、內容雜湊三個方法，**不回傳 token 本身**。M1 只實作檔案版本；寫入方法到切換功能時才加。
  - **憑證指紋** = refreshToken 的 SHA-256 前 16 個十六進位字元。實測刷新只會更換 accessToken，refreshToken 不變。
  - **內容雜湊** = 排除 `accessToken`、`expiresAt` 之後的欄位子集。絕不對整份檔案做雜湊。
- **使用中帳號的判定**：當前憑證的憑證指紋對上某份憑證快照 → 那個納管帳號就是使用中帳號；對不上 → 使用中帳號是未納管帳號。
- **讀數歸屬**：額度快取的 `accountUuid` 等於某帳號綁定的識別碼，這份讀數才歸屬給它。使用中帳號還沒有屬於它的讀數時，狀態是讀數待更新；不得把讀數歸給目前在用的帳號，除非識別碼對得上。未納管帳號沒有綁定，改以 `oauthAccount` 的識別碼比對：額度快取的 `accountUuid` 等於它，讀數才歸給未納管帳號卡片。
- **綁定**：`add` 當下讀取 `~/.claude.json` 的 `oauthAccount.accountUuid`，和新的憑證快照綁定。直接放進目錄、沒有綁定的憑證快照，要同時符合三個條件才補學綁定：它是使用中帳號、額度快取的識別碼與 `oauthAccount` 的識別碼一致、該識別碼還沒綁給其他帳號。
- **每輪狀態機**：
  - 憑證指紋不變 → 刷新或沒有變化，不記錄。
  - 憑證指紋改變，而且對上某份憑證快照 → 切換，寫入切換紀錄。
  - 憑證指紋改變、沒對上任何快照，但 `oauthAccount` 的識別碼仍等於前一個使用中帳號綁定的識別碼 → refreshToken 被輪替：前一個帳號的卡片標記「憑證快照已失效」，不改寫任何檔案。
  - 其他情況 → 切換到未納管帳號，同樣寫入切換紀錄。

### 工具狀態（寫在納管目錄，預設 `~/.claude-multi/`）

- 帳號鍵的格式是 `claude:<帳號標籤>`，帳號標籤就是憑證快照的檔名去掉 `.json`。資料格式從第一版就帶供應商前綴；通用單位的顯示延到他牌支援時再做。
- 綁定以憑證指紋為鍵、值記帳號識別碼（`accountId`），所以改檔名不會遺失綁定。憑證快照被刪除後，對應的孤兒綁定自動清掉。
- 切換紀錄（ADR-0009）：只追加，每一行記時間（`at`）、帳號識別碼（`accountId`）、`source: observed`。工具狀態的欄位一律叫 `accountId`，不沿用 Claude Code 的 `accountUuid`：其他供應商的識別碼不一定是 UUID。**不記帳號鍵**：標籤可以改名，紀錄事後無法補寫。
  - 切到納管帳號：記它綁定的識別碼；切到未納管帳號：記 `oauthAccount` 的識別碼。
  - 兩者都拿不到（例如快照還沒有綁定、或 `.claude.json` 讀不到）：仍然追加一行，帳號識別碼記為 `null`；報表把這段時間標為未歸屬。
  - 與綁定一樣放在納管目錄的工具狀態裡、收緊權限，不顯示在畫面上。
- 待命帳號的最後讀數（`readings.json`）：額度快取同一時間只有一個帳號的讀數，所以每份歸屬到納管帳號的讀數，都以帳號識別碼為鍵存下 `cachedUsageUtilization` 原文，讀回時重新解析；重新啟動後待命帳號仍顯示最後一次觀測的讀數。只留還有綁定的帳號，移除帳號時一併清掉；權限與綁定同樣收緊，不顯示識別碼。
- 最後運作時間：每輪更新。
- 視窗位置。設定不放這裡，另存在設定檔（見〈路徑與設定檔〉）。
- **原子寫入規範**：
  - tmp 檔一律建在目標檔案的同一個目錄，不能用系統暫存目錄；跨磁區時，替換會直接失敗，而這個錯誤在開發機上測不出來。
  - tmp 檔名帶明確的工具前綴。
  - 遇到權限錯誤（防毒或索引服務短暫鎖住檔案）時重試 3 次，每次間隔 50 ms。
  - 失敗時清掉殘留的 tmp 檔。
- 永不寫入 Claude Code 維護的任何檔案（預設位置是 `~/.claude.json` 與 `~/.claude/` 底下；位置依〈路徑與設定檔〉解析）。

### 核心與看板（測試縫 ①）

- 核心物件接收兩個參數：解析後的路徑（見〈路徑與設定檔〉與測試縫 ③）與時鐘。對外只提供四個操作：
  - **poll**：回傳看板。
  - **add(標籤)**
  - **remove(標籤)**
  - **import(憑證檔, 標籤)**：把一份憑證檔複製進納管目錄成為憑證快照；驗證與權限收緊同 add，但不決定綁定（沿用「直接放進目錄」的補學規則）。收緊權限與驗證憑證都在核心，畫面層不另寫一份。
- 每 5 秒比對一次來源檔案的修改時間，有變化才解析（沒變化時沿用上一次的解析結果，見〈資料來源與解析〉的「一輪」）。
- **看板**只帶語意狀態，不帶任何文案。每張卡片的內容：
  - 帳號鍵
  - 角色：使用中、待命、未納管
  - 讀數狀態：有讀數、讀數待更新、尚無讀數
  - 讀數年齡、是否為落後讀數
  - 各限額：種類、百分比或「無計時中窗口」、嚴重度、重置時間或「未知」
  - 鎖定原因
  - 憑證快照到期時間（不是天數；倒數由畫面層算）、到期警示、憑證快照已失效旗標
  - 展開模式專用資料：週窗口用量去向、起訖時間、額外用量、花費、金額欄位；有值或已啟用才帶
- 看板的全域狀態：結構變更橫幅，以及最後一次成功讀數的時間；這一輪的時間與設定檔目前的倒數格式，供畫面層算倒數；設定檔目前的偏好，以及值不合法、改用預設的欄位名稱。
- **落後讀數**的判定：使用中帳號的讀數觀測時間之後，本機的 Claude Code 對話紀錄有更新的修改。掃描頻率可以低於 poll 的頻率，具體做法和成本由實作決定。待命帳號永遠不判為落後。
- 憑證快照到期時間取自 `refreshTokenExpiresAt`（毫秒時間戳）；剩不到設定的天數（`providers.claude.expiryWarningDays`，預設 7 天；含已過期）發出警示，每輪以當下時間與設定檔目前的值重判。門檻用「剩不到」而不是「≤」：倒數一律捨去，剩 7 天又幾十分鐘時畫面是「7天0小時」，若以 ≤ 7 天判定，同一個畫面會前後出現「沒警示」與「有警示」；改成剩不到 7 天，畫面顯示「6天23小時」（或「6.9天」）起才警示，顯示與警示永遠一致。
- **倒數格式**（工作階段窗口、週窗口的重置，與憑證快照到期，三者共用）：倒數＋絕對時間，例如「2小時15分後（14:00）」「28天0小時後（10-27 01:53）」。
  - 兩個單位：剩一天以上是「天＋時」，不到一天是「時＋分」，不到一小時只顯示「分」。不足的部分一律捨去，不進位（進位會高報剩餘時間）。
  - 設定 `countdownFormat`（只能在設定檔調整，不進右鍵選單）可改成 `decimalDays`：剩一天以上顯示天數到小數第 1 位（捨去，例如 6.99 天顯示「6.9天」）；不到一天時同樣改顯示「時＋分」，否則工作階段窗口永遠是「0.x天」。
  - 絕對時間是本機時區；24 小時內只顯示時刻，更遠的加上月日，不顯示年份。一律顯示，不開放關閉。
  - 憑證快照已過期顯示「已過期（到期時間）」，不顯示負的倒數。

### 命令列

- **入口**：單一入口，以 `python -m <套件名> <子命令>` 執行，純標準庫、零安裝；子命令為 `add`、`remove`、`list`，另有架設者檢查指令。README 與未納管帳號卡片都引用這個完整寫法。
- **`add <標籤>`**：
  - 複製當前憑證成為憑證快照，並綁定 `oauthAccount` 的識別碼；標籤已存在時覆寫，重新納管就是走這條路。
  - 主動收緊權限：Windows 移除繼承、只授權目前使用者；POSIX 目錄設 700、檔案設 600。事後驗證，不符合就修正並告警（ADR-0007）。
  - 標籤看起來像 email 時提示。
- **`remove <標籤>`**：刪除憑證快照並清掉綁定。
- **`list`**：把看板渲染成文字。
- 本工具不讀取也不儲存 email。

### 畫面層（測試縫 ②，ADR-0004）

- **三種版面**，都只是同一份看板的渲染器，彼此不共用版面程式碼：
  - **A 卡片列表**：一個帳號一張卡片，限額逐列顯示名稱、百分比、膠囊進度條、重置時間。精簡模式只顯示使用中帳號那一張。
  - **B 密集表格／單行條**：精簡模式是一行橫條（帳號標籤、兩個窗口的小進度條與百分比、讀數年齡、提示數量）；展開模式是表格，一列一個帳號，欄位是工作階段窗口、週窗口、讀數年齡、憑證到期倒數，提示接在該列下方。
  - **C 環形儀表**：外圈是週窗口、內圈是工作階段窗口，中央顯示工作階段百分比；展開模式每列三個帳號。
  - 同一時間只建立目前選用的那一種版面；切換版面時，舊版面的物件要整批銷毀。
- **視覺風格（D 精修，三種版面共用）**：圓角視窗（以透明色鍵挖出圓角，Windows 10 也適用）、圓角卡片加淡陰影、膠囊形進度條、「使用中／待命」狀態標籤、百分比使用較大的數字字型、提示前面加嚴重度色點；B 版展開時，使用中帳號那一列加淡色底。
- **設計 token 集中在一處**：兩套主題的顏色、字型、字級、圓角、間距都定義在同一個地方，三種版面只引用 token，不寫死數值。換色、換字只改 token；改版面結構才需要動該版面的繪製程式。
- **配色規則**（兩套主題、三種版面都適用；token 測試守住可機械判定的部分）：
  - **對比量實際的那一對**：前景對它**實際畫在上面**的顏色量（進度條填色對底軌、標籤文字對標籤底色），不是對視窗或卡片底色。兩套主題的每一對都要各量一次，淺色過了不代表深色過。
  - **兩套標準都要過**：WCAG 2 是下限——文字 4.5:1（≥18pt 或 ≥14pt 粗體的大字 3:1）、進度條與色點等圖形 3:1。APCA 是設計目標——非內文文字（標籤、數值、附註）|Lc| ≥ 60、UI 元件 |Lc| ≥ 30；任何需要被看見的元素（包括空的進度條底軌）不低於 |Lc| 15。
  - **一個 token 只用在它的角色**：token 以角色命名，不因為色值剛好合適就借用別的角色；缺角色就新增 token。
  - **一色一義**：同一個顏色在整個介面只代表一種意思。`accent` 代表「使用中帳號」；嚴重度三色只代表嚴重度；中性資訊（例如週窗口已過幾 %）不用這兩類顏色。
  - **顏色不是唯一的訊號**：嚴重度一定同時有百分比數字或文字提示，不能只靠顏色表達。
  - **深色主題不是淺色主題的反轉**：深色要另外調整，並逐對重量。
  - 對比不足時只調明度、保持色相，避免修對比變成換配色。
  - **例外**：B 版使用中那一列的淡色底要淡才不壓過內容，所以它本身對卡片、以及畫在它上面的空進度條底軌，不受「不低於 |Lc| 15」約束（使用中另有狀態標籤標示）；列上的文字與圖形仍要對淡色底逐對量過。為此淺色主題的嚴重度三色再調深一級，A 版跟著用同一組。
- UI 原型保存在拋棄用分支 `prototype/widget-ui` 上，作為視覺參考；啟動方式寫在該分支原型檔的檔頭。原型採「每次整個重建」的寫法，**不可直接沿用**，要依本節的物件生命週期規則重寫。

- 只用 Python 標準庫，加上純 `tk` widget 與 Canvas；不用 `ttk`、不用 Pillow；以 `pythonw` 啟動；Windows 上開啟 DPI 感知。
- 畫面層只把看板渲染出來，不含任何判斷邏輯。判準：畫面層可以換算與上色（例如用起訖時間算出週窗口已過幾 %、依到期時間已過或未過選紅或黃），不可以決定要不要警示；要不要警示由核心放進看板（例如 `snapshot_expiring`、`lagging`）。
- **物件生命週期**：每輪只更新既有 widget／item 的屬性，不建立新物件；必須建立的物件要有對應的銷毀路徑。精簡模式不建立展開模式的 widget，展開模式的 widget 延遲建立。`after()` 不重複註冊，`StringVar` 不累積。
- 語系檔有正體中文與英文兩份，預設跟隨系統語系，不支援時退回英文。所有文案都在畫面層套用。
- **文案規則**（票 24，2026-09-30）：卡片上的提示盡量單行、不靠折行撐長；補救步驟不放卡片，卡片只提醒要做什麼，步驟寫在 README 與命令列 `list`。兩個語系下，任兩個文字 item 的外框都不得重疊（縫 ② 有測試守住）。

### 設定

- **右鍵選單不能變長**：只放常切換的偏好。數值型、進階或按供應商分開的設定（`providers` 底下）只放設定檔，不進選單。之後設定項若多到選單放不下，改成「右鍵 → 設定」開一個設定頁面、設定都在裡面調整；這會推翻下一條的「不另開設定視窗」，屆時再議。
- 設定入口是視窗的右鍵選單，不另開設定視窗；各項切換後立即生效，不跳確認。也可以直接修改設定檔（見〈路徑與設定檔〉）；GUI 是主要入口。帳號管理（納管、移除）命令列與 GUI 都能做，兩者呼叫同一組核心操作。
- **右鍵選單的設定項**（M1 只有這些）：
  - 版面：A 卡片列表（預設）、B 密集表格／單行條、C 環形儀表。
  - 置頂：開關，預設開啟。
  - 模式：精簡／展開。雙擊視窗也能切換。
  - 語系：跟隨系統（預設）、正體中文、English。
  - 主題：跟隨系統（預設）、淺色、深色。選「跟隨系統」時讀取 Windows 的應用程式深淺色設定，每輪 poll 檢查一次，系統切換後跟著切換。嚴重度配色在兩種主題下都要清楚可辨。
  - 透明度：100%（預設）、85%、70% 三段。
  - 開機自動啟動：開關，預設關閉（做法見下）。
- **右鍵選單的動作**：
  - 納管目前登入的帳號…：跳出標籤輸入框，呼叫核心的 `add`，行為與命令列相同（含 email 標籤提示、權限收緊）。
  - 匯入憑證檔…：選一個憑證檔複製進納管目錄，標籤預設取檔名去掉 `.json`；同樣收緊權限，綁定沿用「直接放進目錄」的補學規則。
  - 開啟納管目錄、結束。
- **自動記住、不列進選單**：視窗位置。上次的位置已經不在任何螢幕內時，移回主螢幕。
- **固定值，不開放設定**：輪詢間隔 5 秒；精簡模式固定同時顯示工作階段窗口與週窗口。（百分比門檻與憑證到期警示天數已改成設定，見〈路徑與設定檔〉的 `providers`。）
- 開機自動啟動：寫入**目前使用者**的登入啟動項（Windows 登錄的 Run 機碼，以 `pythonw` 啟動本工具），關閉時移除。只改動本工具自己的那一個值，用標準庫的 `winreg` 操作。開關的顯示狀態以登錄的實際值為準，不另存一份，避免使用者手動刪除後兩邊不同步。預設關閉。
- 這項設定不動到 Claude Code 的任何設定（ADR-0006 不受影響）。

### 路徑與設定檔（ADR-0008）

- **設定檔**固定放在 `%APPDATA%\cc-quota-tracker\settings.json`，不放在納管目錄裡。內容是八項偏好（版面、置頂、模式、語系、主題、透明度、倒數格式、字型）、按供應商分開的設定 `providers`，加上兩個路徑欄位。視窗位置是工具狀態，開機自動啟動以登錄檔為準，兩者都不寫進設定檔。
- **按供應商分開的設定**（`providers`）：各家的窗口、憑證壽命、嚴重度規則都可能不同，所以與供應商相關的門檻放在 `providers.<供應商>` 底下，不共用。預設值由各供應商自己帶入，設定檔只覆寫。Claude 有三項：
  - `expiryWarningDays`：憑證快照剩不到這麼多天就警示，預設 7。正整數，不設上限。
  - `warningPercent`、`criticalPercent`：供應商沒給嚴重度時的百分比門檻，預設 60、85。1～100 的整數，warning 必須小於 critical。
  - 值不合法、缺少、或 `providers` 整段讀不懂時，該項用供應商的預設；兩個百分比門檻不是由小到大時，兩個都用預設。改了下一輪就生效。
  - 工作階段窗口與週窗口的長度不是設定：本工具沒有寫死 5 小時或 7 天，重置時間一律取自供應商給的 `resets_at`，供應商調整窗口長度時不必改程式。
- **字型**（`font`，只能在設定檔調整，不進右鍵選單）：預設 `null`，使用設計 token 裡的內建字型（Windows 內建的微軟正黑體 UI，百分比數字用 Segoe UI Semibold）。填入字型家族名稱時，所有文字都改用它，字級與字重仍取自設計 token。不論內建或自填，字型不存在時一律改用系統預設字型（tk 的 `TkDefaultFont`），不能讓 tk 自行替換成其他字型——tk 找不到字型時會改用 Arial，中文要靠系統補字才顯示得出來。
- 第一次啟動時寫出完整的設定檔：每個欄位都填上預設值，路徑欄位寫 `null`。JSON 不能寫註解，欄位說明放在 README。
- **Claude Code 目錄**（額度快取與當前憑證所在的位置），依序取第一個有值的：
  1. 設定檔的欄位
  2. 環境變數 `CLAUDE_CONFIG_DIR`
  3. home 預設（`~/.claude.json` 與 `~/.claude/`）

  設定檔欄位的語意與 `CLAUDE_CONFIG_DIR` 相同。之所以多這一層，是因為開機自動啟動只會繼承 Windows 使用者層級的環境變數。
- 設了 `CLAUDE_CONFIG_DIR` 之後，`.claude.json` 與 `.credentials.json` **都在該目錄裡面**，不是它的上一層。與 home 預設不對稱：預設時 `.claude.json` 在 home、憑證在 `~/.claude/`。
  - `.claude.json`：實測（票 21，2026-09-28，Claude Code 2.1.x）：把 `CLAUDE_CONFIG_DIR` 指向空目錄後執行一個不需登入的子命令，`.claude.json` 寫在該目錄裡（另附一個 `backups/`），home 底下的 `.claude.json` 修改時間不變。
  - `.credentials.json`：依官方文件；沒有實測（要在該目錄裡實際登入一次）。
  - 環境變數是空字串時，視為沒設。
- **納管目錄**依序取第一個有值的：設定檔的欄位 → home 預設 `~/.claude-multi/`。
- **路徑欄位**：
  - 缺少或為 `null`：視為沒填，往下一層找
  - 有填、但目錄不存在：直接報錯，**不回退**。回退到 home 會讀到另一組帳號，而且畫面看起來一切正常
  - 有填、但不是絕對路徑（含空字串與非字串）：同樣報錯。相對路徑以工作目錄為準，而開機自動啟動時的工作目錄不同，會靜默指到別處
  - 錯誤訊息指出是哪一個欄位，並附上設定檔的位置
- 納管目錄不得位於解析出的 Claude Code 目錄裡面（含兩者相同），否則報錯並指出 `managedDir`：本工具永不寫入 Claude Code 目錄底下的任何檔案。
- 路徑只在啟動時讀；改了路徑，看板提示「需重新啟動」。命令列與 GUI 使用同一套解析。
- 三層都沒有指定、home 預設位置也找不到 `.claude.json` 時，看板要提示「可能讀錯位置」，不能只顯示成尚無讀數。
- **偏好**每一輪依設定檔的修改時間重讀，改了就生效。GUI 寫入時，先重讀設定檔、只改那一個欄位，再原子寫入，避免蓋掉使用者剛手改的內容。
- **設定檔內容有問題時**：
  - 整個檔案不是合法的 JSON：全部使用預設值並提示；GUI 的改動只在記憶體生效，**不寫回檔案**，直到使用者修好為止
  - 單一欄位不合法：只有那一欄使用預設值，提示列出欄位名稱

### 架設者工具

- 提供一支檢查指令，驗證工具依賴的欄位路徑仍然存在且型別正確，並列出 `utilization` 底下新出現的未知欄位。
- 檢查指令同時印出實際使用的 Claude Code 目錄與納管目錄，並註明各自來自設定檔、環境變數或預設值。

## 測試決策（Testing Decisions）

- **好的測試只看外部行為**，只透過三道縫觀察：
  - **縫 ①**：核心的 poll／add／remove／import 回傳的看板，以及它寫進工具狀態目錄的檔案。
  - **縫 ②**：畫面層渲染後的 Canvas item 數量。
  - **縫 ③**：啟動時的路徑解析：輸入 home 目錄與環境變數，輸出解析後的路徑、各自的來源、設定檔位置，以及它寫出的設定檔；有填但不能用的路徑欄位以錯誤帶出欄位名稱。命令列與 GUI 都呼叫它，檢查指令印出的路徑來源也取自它。
  - 不直接測解析層或狀態機的內部函式。
- **縫 ③**：測試把環境變數整組換成測試給定的值（不讀真實的 `CLAUDE_CONFIG_DIR`、`APPDATA`），設定檔寫在暫存目錄裡。至少涵蓋：第一次啟動寫出完整設定檔、已存在不覆寫、三層優先順序、`null`／缺少往下一層、目錄不存在或不是絕對路徑時報錯且不回退、設定檔不是合法 JSON 時路徑當成沒填且不覆寫。看板上的三個提示（可能讀錯位置、需重新啟動、設定檔無法讀取）從縫 ① 觀察。
- **縫 ①**：測試把 home 指到暫存目錄，放入假的 `.claude.json`、憑證檔、憑證快照與對話紀錄檔，由測試控制時鐘。至少涵蓋以下情境：
  - 刷新（只換 accessToken）不產生切換紀錄
  - 切換後第一輪就判對使用中帳號，並處於讀數待更新，直到額度快取的識別碼對上
  - 舊帳號的讀數不會歸屬給新帳號
  - `resets_at` 為 null 顯示為無計時中窗口；過了 `resets_at` 也顯示為無計時中窗口，重置時間標為未知（週窗口則標為已重置）；`is_active: false` 但重置時間在未來，照常顯示百分比
  - 移除 `cachedUsageUtilization` → 尚無讀數，不亮橫幅
  - 截斷的 JSON → 沿用上一次的值，不亮橫幅
  - 把 `limits` 改成錯誤型別 → 第 3 輪才亮橫幅，並帶出最後一次成功的讀數
  - 不認得的 `kind` 或未知的限額欄位 → 歸入其他限額
  - 不認得的嚴重度當 `normal`；嚴重度缺失時退回百分比門檻
  - 憑證快照 5 天後到期 → 發出警示
  - 輪替情境 → 前一個帳號標記失效，憑證快照的檔案內容不變
  - 憑證指紋對不上任何快照 → 未納管帳號卡片
  - `add` 會綁定識別碼；在 Windows 的真實暫存目錄上驗證權限確實收緊
  - 改掉憑證快照的檔名之後，綁定仍然保留
  - 多輪 poll 加上 `add` 之後，`.claude.json` 與 Claude Code 設定檔的修改時間都不變
  - 閒置時的舊讀數不算落後；對話紀錄在讀數之後有更新 → 判為落後讀數；待命帳號永遠不算落後
  - 最後運作時間每輪都會更新
- **縫 ②**：同一個 widget 連續渲染 N 次看板，期間在精簡和展開模式之間、淺色和深色主題之間來回切換，`len(canvas.find_all())` 在每次回到同一模式時都相同。切換主題只改屬性，不重建 item。**A、B、C 三種版面各跑一次**；另外在三種版面之間來回切換 N 次，回到同一版面時 item 數也要相同，以此確認舊版面的物件有銷毀乾淨。
- **不寫成自動測試、改在驗收時手動做的項目**：
  - 記憶體上限（展開模式、顯示所有帳號卡片時，Private ≤ 20 MB、WorkingSet ≤ 35 MB）
  - 真實切換後 5 秒內高亮正確
  - 和 `/usage` 對話框並排比對數字
  - 用 `git ls-files` 逐檔確認沒有真實帳號、email、識別碼、雜湊值或個人路徑
  - 開啟開機自動啟動，重新登入 Windows 後確認視窗自動出現；關閉之後，登錄裡的值已被移除
- 測試框架用標準庫的 `unittest`，維持零安裝依賴。repo 目前沒有既有測試可以參考。

## 範圍外（Out of Scope）

- 從工具內切換帳號、把憑證寫回憑證快照、DPAPI 加密：屬於第二版的切換功能。
- token 報表：這一版只累積切換紀錄和最後運作時間。
- 其他供應商（Gemini、Codex 等）與通用單位顯示。設定檔的 `providers` 已經按供應商分開，這是會被使用者手改、之後難以搬遷的格式，所以先做；程式架構等第二家供應商時再做。
- 打包成 exe：M1 以原始碼部署。打包後的記憶體、開機自動啟動指向 exe、無命令列時的操作方式，留到之後再評估。
- macOS 與 Linux：額度快取的路徑三個平台相同，但 macOS 的憑證放在 Keychain，要另外實作一套憑證儲存。
- 任何網路請求，包括以 API 作為退階資料源（ADR-0001）；自備 statusLine 腳本作為第二資料源。
- 任何以額度為觸發條件的自動化（ADR-0005）。
- 修改 Claude Code 的設定、掛 statusLine 或 hooks（ADR-0006）。
- 顯示或儲存 email，以及自訂顯示名稱。
- 「立即更新」按鈕：資料每 5 秒從本機檔案重讀一次，按了數字也不會變；額度快取只由 Claude Code 自己更新（登入、使用中的面板、發出 prompt 時）。
- 可調整的輪詢間隔，以及其他固定值。

## 補充說明（Further Notes）

- 透明度先做三段固定值；之後可能改成拖拉滑桿或自訂數值，到時再議。

- **尚未驗證的假設**：「`claude login` 會立刻更新 `oauthAccount`」。refreshToken 輪替的判定建立在這個假設上。refreshToken 會不會在接近到期時輪替，目前也還沒有觀察到。建議在實作前先做一次唯讀取樣：手動切換帳號，前後各記錄一次憑證指紋、`oauthAccount` 識別碼、額度快取識別碼和各限額的狀態，之後每分鐘記錄一次，直到額度快取的識別碼翻轉。這樣可以同時量到讀數待更新會持續多久。取樣時只輸出識別碼的雜湊前綴，不輸出原值。
- **取樣結論（票 01，2026-09-28，兩次手動切換、取樣間隔 30 秒與 5 秒）**：
  - `claude login` 切換帳號後，憑證指紋、`oauthAccount` 識別碼、額度快取識別碼**在同一個取樣間隔內一起翻轉**：假設成立，切換偵測可照本文實作。
  - 額度快取的觀測時間落在翻轉前 2 秒內，且使用者**沒有發過 prompt**：登入動作本身就會更新額度快取。以這種方式切換時，「讀數待更新」實際持續時間小於 5 秒，不是「要等發 prompt」。
  - 不變的部分：「讀數待更新」狀態仍要保留（直接放進目錄的憑證快照、登入後快取更新失敗、之後由本工具寫回憑證的切換，都可能出現），但**文案不得再寫成「一定要發 prompt 才會出現」**。影響使用者故事 23、26 與 README 說明的措辭。
  - 樣本中出現 `is_active: false` 但 `percent` 不為 0 的工作階段限額（63%）。
- **`is_active` 的語意更正（票 03，2026-09-28）**：本機 Claude Code 對同一組欄位的 schema 說明寫明 `is_active` 是「單值指示器該顯示哪一列」；實測當下工作階段限額 63%、重置時間在 1.5 小時後、`is_active: false`，週窗口 83%、`severity: warning`、`is_active: true`。原本「`is_active: false` 顯示為無計時中窗口」會把計時中的窗口誤顯示成無計時中窗口，已改為只看 `resets_at`（見〈資料來源與解析〉）。同一份 schema 也確認 `severity` 的值域與 `weekly_scoped` 的 `scope` 結構。
  - 未觀察到：refreshToken 輪替（兩次翻轉時 `oauthAccount` 都同步改變）。輪替判定仍是未驗證的假設。
- 實測值（供設計參考）：額度快取在面板模式下會持續更新，量測當下的新鮮度是 13–20 分鐘；檔案約 0.1 MB，解析約 1 ms；週窗口固定 7 天。
- 憑證快照的 refreshToken 壽命是 30 天，到期後一定要重新登入該帳號並重新納管。這是使用者一定會碰到的事，所以到期警示屬於第一版的必要功能，不是加分項。
- **結構不同的憑證快照（票 08，2026-09-29）**：實測在納管目錄發現一份憑證快照，頂層除了 `claudeAiOauth` 還多一個 `organizationUuid`，`claudeAiOauth` 裡沒有 `refreshTokenExpiresAt`；方案、scopes、refreshToken 與其他快照相同，建立時間在一天之內，所以不是舊版 Claude Code 的格式，來源未確認。**暫當無效資料、不另外處理**：這種快照沒有剩餘時間，也不發到期警示。需要時由使用者在該帳號下重新登入、重新 `add`，換成一般格式的快照。
